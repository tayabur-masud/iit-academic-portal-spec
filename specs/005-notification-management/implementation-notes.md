# Implementation Notes: Notification Management

- **Producers never wait.** `NotificationRequestService` uses its own short-lived database contexts (from the context factory), not the request's, so it cannot share a transaction with, or leave pending changes in, the caller's unit of work, and a failure there cannot undo a committed action. It also never throws. Admin mutations (template save, resend, reminder setting) are the opposite: they use the request's context so their audit event commits with the change.
- **One worker pass** (`NotificationDispatchProcessor`) does three things: resolve retained password-recovery requests into notifications, run the feedback-reminder scheduler, and deliver due notifications. In tests the worker is off and `FlushNotificationsAsync` runs the same pass; `CapturingEmailSender.Pump` lets a test that waits for an email drive it.
- **Uncertain on purpose.** A timeout or lost connection after the request left, and a worker that dies after marking the provider call started, both end Uncertain. This trades some Uncertain records for never sending a possible duplicate security email. Only Failed records can be resent.
- **Security content.** The worker asks the owning workflow's provider for fresh values per attempt, renders them in memory, and drops them. Failure codes are short classifications (letters and digits, 64 at most); provider messages, addresses, and bodies never reach attempts, state, logs, or audit events. Tests assert this for a failing provider that echoes the address and body.
- **Invitation gate.** Teacher provisioning requests a `TeacherInvitation` after its transaction commits (a rolled-back creation requests nothing). With no secure setup-link provider the notification fails with `SetupLinkProviderMissing` and is visible and resendable; the account stays pending. This is deliberate and is the reason task T016 stays open.
- **Password recovery.** `PasswordRecoveryService.RequestAsync` retains the protected address (Data Protection) and answers generically whatever happens. The worker resolves the account, requests one `PasswordReset` notification keyed by the retained request, and deletes the request; processing the same request twice makes one notification. `PasswordResetContentProvider` re-checks that the account still exists and still has the address the request was accepted for before it generates a proof.
- **Retained request lifetime** is its own setting because proof lifetime starts later, when the proof is generated; tying them together broke the expired-proof test harness and would also have discarded requests for the wrong reason.
- **Why `ExecuteDelete` is not used** for transient rows: a source-scanning guard test forbids it anywhere in the service so audit history can never be bulk-deleted. The transient rows are removed by key instead.
- **Test host.** `NotificationTestHost` adds a scripted provider (`Emails.Behavior`), a store-failure switch scoped to the host, a recording failure signal, a fake feedback-window owner, and isolated Data Protection keys.
- **Branded layout.** `EmailLayout.Render(subject, plainBody, logoUrl)` is a pure function that HTML-encodes every piece of text, turns only whole http(s) addresses into links, and turns an address on a line of its own into a button with the address repeated as text beneath it. The processor builds it just before the provider call and passes it as `EmailMessage.HtmlBody`; Brevo gets `htmlContent` plus `textContent`, SMTP gets an alternate view. The branding values come from `NotificationOptions.Branding` (an `EmailBranding` record) and are validated at startup by `NotificationOptionsValidator`: the color must match `^#[0-9A-Fa-f]{6}$` (it is written into a style, so only that shape is allowed) and must reach a 4.5:1 contrast ratio with the white button text, the logo address must be absolute https, and the text settings are single-line, non-empty, and at most 300 characters. An invalid value stops the service from starting. Because it is built per send, a branding or layout change applies to messages not yet sent and nothing HTML is ever persisted. The preview endpoint returns the same HTML and the editor shows it in a sandboxed frame (`sandbox=""`, no scripts).
- **Lazy loading.** The notification screens are loaded on demand so the initial bundle stays under its budget.
- **Bug the tests caught:** a `type="number"` input gives the form a number or null, not text; the reminder setting treats it that way.
