# Course Management Data Model

**Status**: Implemented by the `Courses` migration; see [implementation-notes.md](implementation-notes.md).

## Course

One course-catalog entry owned by exactly one Degree.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | UUID | Yes | Stable primary key, generated by the application. |
 | `name` | String | Yes | Display name; normalized for search. Names are not unique-constrained; multiple Courses may share a name. |
| `code` | String | Yes | Display code with a normalized comparison value; unique across all non-deleted Courses, including inactive ones. |
| `creditHours` | Decimal(8,2) | Yes | Must be greater than zero and have no more than two decimal places. |
| `theoryCreditHours` | Nullable Decimal(8,2) | No | Optional; if supplied, must be between zero and `creditHours`, inclusive, and have no more than two decimal places. |
| `labCreditHours` | Nullable Decimal(8,2) | No | Optional; if supplied, must be between zero and `creditHours`, inclusive, and have no more than two decimal places. |
| `type` | Enum/string | Yes | Exactly `Mandatory` or `Elective`. Persist using the existing string-enum convention. |
| `degreeId` | UUID | Yes | Foreign key to an existing Degree. Degree changes must preserve all prerequisite relationship rules. |
| `prerequisiteCourseId` | Nullable UUID | No | Optional self-reference to a different, active Course in the same Degree. The graph must remain acyclic. |
| `isActive` | Boolean | Yes | Defaults to true. A Course referenced as prerequisite by any active Course cannot be deactivated. |
| `createdAtUtc`, `createdByUserId` | UTC timestamp, nullable account ID | Yes / No | Inherited audit fields, stamped server-side on creation. |
| `lastModifiedAtUtc`, `lastModifiedByUserId` | UTC timestamp, nullable account ID | Yes / No | Inherited audit fields, stamped server-side on every committed update or deactivation. |

The entity also inherits the configuration record's internal soft-deletion state for consistency with the shared persistence model. Course Management exposes deactivation, not a delete operation.

## Relationships

- `Course.degreeId` references one `Degree`; use `ON DELETE RESTRICT` and index the FK.
- `Course.prerequisiteCourseId` optionally references `Course.id`; use `ON DELETE RESTRICT` and index the FK.
- Each Course has at most one direct prerequisite. Prerequisites may form a longer chain, but never a cycle.
- A prerequisite must be active and in the same Degree. Updates to a Course's Degree must not invalidate either its own prerequisite or any active Course that depends on it.
- The existing append-only audit system records each successful Course create, update, and deactivation in the same transaction as the entity change.

## Validation and Integrity

- Required strings are trimmed/normalized using existing configuration helpers; codes use the shared code normalizer.
- The code unique index applies to non-deleted rows, including inactive rows. Application validation returns a field-keyed error; the database index protects against races.
- `creditHours > 0`; each supplied breakdown value is between zero and `creditHours`, inclusive.
- When both `theoryCreditHours` and `labCreditHours` are non-null, their sum equals `creditHours`. A database check can enforce this conditional equality as well as non-negativity.
- `degreeId` must resolve to an active Degree on create or change. Reject a Degree change if it would make the Course's own prerequisite or any active dependent Course's prerequisite cross-Degree; no affected Course may be modified on rejection.
- `prerequisiteCourseId` must resolve to an active Course, must not equal the Course's own ID, and must share its Degree. Application validation walks the prerequisite chain and rejects a cycle before saving.
- An update setting `isActive` to false is rejected if any active Course references the target as its prerequisite. It must not change either record on rejection.
- Course data and its business audit event commit together; a failure in either leaves neither committed.

## Lifecycle

1. **Create**: Save a Course as active by default after validating its Degree, code, type, credit values, and optional prerequisite.
2. **Update**: Change catalog fields while preserving valid Degree and prerequisite relationships. Revalidate the full affected relationship set when changing a Degree or prerequisite.
3. **Deactivate**: Set `isActive` to false only when no active Course uses this Course as a prerequisite. Deactivation is a normal audited update, not a cascade.
4. **Reactivate**: If the shared active-state control supports reactivation, revalidate prerequisite and Degree integrity before making the Course selectable again.

## Database Migration

Add a `Courses` table with inherited audit and configuration columns; Course-specific scalar fields; restrictive Degree and self-referencing foreign keys; a partial unique normalized-code index for non-deleted rows; indexes on `DegreeId` and `PrerequisiteCourseId`; and check constraints for positive total credit hours, components between zero and total, and conditional theory/lab equality. No existing enrollment or result table is changed by this feature.
