# Implementation Notes: Teacher Management

- **Account status is a persisted `PortalUser.AccountStatus`** (`TeacherAccountStatus`: Active, PendingCredentialSetup, Deactivated), stored as text with a database default of `Active`. `Active` is the enum's zero value on purpose: EF Core treats the CLR default of a property that has a database default as "not set", so a non-default first value would be stored as `Active` and a pending account would be silently created active. A pending or deactivated account fails sign-in exactly like a wrong password (no state is revealed) and its sessions stop matching in `AuthSessionRepository` (touch and lookup), so a status change takes effect on the next request.
- **One transaction per change.** `ITeacherStore.BeginTransactionAsync` wraps the Identity `UserManager` calls (which save on their own), the profile, the session revocation, and the staged audit event, so a failed audit event or validation rolls everything back (tests force an audit failure for create, role change, and deactivation). The last-Admin check takes a PostgreSQL advisory transaction lock first (a no-op on SQLite, whose single writer needs none); a PostgreSQL test proves two concurrent removals leave one Admin.
- **Active Admin** means the Admin role and status Active. A pending Admin does not count.
- **Roles.** The endpoint takes the editable set (Teacher, optionally Admin). Coordinator is carried over untouched and is only ever changed by the synchronizer. A deactivated teacher's roles cannot be changed.
- **Reactivation is not offered.** The data model says only credential setup may make an account Active, and that flow does not exist yet.
- **Audit.** Events `teacher.created`, `teacher.updated`, `teacher.roles.changed`, `teacher.deactivated`, `teacher.coordinator-role.synchronized`. Email and phone are change indicators only (recorded as changed, never with values); an update or role change that changes nothing records nothing.
- **Invitation email (feature 005).** The shared notification capability now exists, and provisioning requests a `TeacherInvitation` after the account commits. Delivery is still blocked: it needs a secure setup-link provider from the account owner, so the notification fails visibly (`SetupLinkProviderMissing`), nothing is sent, and the account stays pending and unable to sign in.
- **Designations** in use by a teacher profile cannot be deleted (`IConfigurationStore.DesignationInUseByTeacherAsync`); the catalog screen offers "Deactivate instead".
- **The synchronizer stages without saving** (see the contract), so its role change and audit event commit with the caller's assignment change.
- **Directory** uses infinite loading over sequential bounded API pages, ordered by upper-cased name then id; search is a case-insensitive contains over name, email, and staff ID. The UI has no numbered pager or page-size selector.
- `TeacherProfile` derives from `AuditedEntity`, so it records who created and last changed it; the edit screen shows the "Record history" card.
- Task notes: the profile-update tests live in `TeacherProfileTests.cs` (T013 asked for them with the role tests), and deactivation through `PUT` with `isActive: false` was added alongside the dedicated `POST .../deactivation` route.
