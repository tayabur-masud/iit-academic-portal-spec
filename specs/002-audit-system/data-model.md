# Data Model: Audit System

**Feature**: [Audit System](spec.md)  
**Status**: Logical design for the existing PostgreSQL 18 / EF Core 10 service. Validate the migration and runtime grants in PostgreSQL before release.

## Modeling Decisions

- Store formal business and security audit events in the existing portal database; do not create another service or database.
- Keep event identity and historical actor/entity identifiers independent of live account and business-row foreign keys so deactivation or deletion does not erase historical identity.
- Treat `eventType` as an extensible, namespaced value. The audit capability defines the common envelope; each owning feature declares its mandatory event types and approved change fields when it integrates.
- Store only allowlisted field names and before/after values. Never store credentials, cookies, session handles, reset proofs, cryptographic secrets, or unapproved personal data.
- Use a durable PostgreSQL security-event outbox with idempotent delivery to the formal event store. Keep the outbox mutable for delivery status; formal audit events remain immutable to application and runtime DB roles.
- Use a migration/DDL owner distinct from the runtime application role. Runtime grants on the formal audit-event store are limited to `SELECT` and `INSERT`; runtime credentials must not own the table.
- Do not configure retention, automatic deletion, or archival without an approved institutional policy. Archival is a separate future lifecycle and must preserve authorized retrieval.

## Logical Entities

### Audit Event

An immutable record of a mandatory business action or security action. Routine diagnostics are not formal audit records by default.

| Attribute | Meaning | Constraints |
|---|---|---|
| Event ID | Stable identifier and idempotency key | Required, unique, generated by the trusted server before persistence |
| Occurred at UTC | Time the action/outcome occurred | Required, UTC; immutable after insert |
| Category | Formal event class | Required: `business` or `security` |
| Event type | Namespaced action identifier | Required, extensible, at most 100 characters; owning feature declares mandatory types. Initial security types: `auth.sign-in`, `auth.password-reset.completed`, `auth.session.revoked`, `auth.role.switched`, `access.denied`, `audit.mutation.attempted`, `audit.review.accessed` |
| Outcome | Result of action | Required: `success`, `failure`, or `denied` |
| Actor user ID | Stable actor identifier | Nullable for unauthenticated/system activity and failed sign-ins; no live-user FK that would cascade-delete history; no display name or email is stored |
| Entity type | Type of affected record | Nullable when no target is known; at most 100 characters |
| Entity ID | Stable identifier of affected record | Nullable when no target is known; at most 200 characters; stored without a live-entity FK |
| Correlation ID | Request/workflow correlation | Always server-generated for events raised during an HTTP request; nullable only for events with no request; at most 100 characters |
| Source | Client IP address derived from trusted forwarded headers | Nullable when no request exists; at most 45 characters; no user-agent or other client-supplied value |
| Metadata | Safe action context | Optional structured values; only data approved for this event type; at most 4 KB. Access-denied events store the matched route template and HTTP method, never the raw path or query string |
| Change summary | Allowlisted field changes | Optional entries of field name and safe previous/new values, or a safe changed indicator; never contains non-allowlisted values; at most 16 KB |

**Invariants**:

- Events are append-only. No application API or ordinary application service updates/deletes them.
- Actor and entity IDs are historical identifiers and remain reviewable if the related account/entity is later deactivated or removed.
- Replays use the same Event ID; duplicate delivery does not create another event.
- `failure` describes an unsuccessful operation; `denied` describes a policy or authorization denial. Business-policy denials are business events; access-control denials are security events.

### Security Audit Outbox Item

Durable internal work record used to deliver security events without changing the primary authentication/authorization result.

| Attribute | Meaning | Constraints |
|---|---|---|
| Event ID | Stable key matching the eventual Audit Event | Required, unique; primary idempotency key |
| Safe event envelope | Event content awaiting formal persistence | Required; already redacted/allowlisted before enqueue |
| Enqueued at UTC | Time accepted for durable delivery | Required, UTC |
| Delivery state | Current delivery lifecycle | Required: `Pending`, `RetryScheduled`, `Exhausted`, `Delivered`, or `Handled` |
| Attempt count | Number of delivery attempts | Non-negative; incremented for every attempt |
| Next attempt at UTC | Earliest scheduled retry | Nullable when not scheduled |
| Last attempt at UTC | Most recent worker attempt | Nullable before first attempt |
| Last failure code | Safe classified cause | Nullable; no secrets or raw exception payload |
| Lease until UTC | Short claim held by the worker processing the item | Nullable; set when a worker claims the item; an expired lease may be claimed again |
| Delivered at UTC | Successful formal event persistence | Nullable until `Delivered` |
| Handled at/by/reason | Authorized recovery action | Nullable; required for `Handled`; reason is safe, actor is a stable historical ID |

**State transitions**:

1. `Pending` is created with the event envelope and stable Event ID.
2. A temporary persistence failure moves it to `RetryScheduled`; the worker schedules another attempt using bounded backoff.
3. Reaching the automatic retry limit moves it to `Exhausted`; the row and envelope remain stored, a protected alert fires, and authorized recovery is required.
4. Successful event insert moves it to `Delivered`. A duplicate Event ID is treated as already delivered and safely acknowledged.
5. An authorized recovery process may retry an `Exhausted` item or set it to `Handled` with actor/time/reason. It may not silently discard the envelope. A retry also stamps Handled at/by/reason with the operator, time, and reason of the recovery action, so the history of who re-queued an item is kept; the item is `Pending` again.

A worker claims an item by setting a short lease with a conditional update, so only one of several service instances processes it at a time. A crashed worker's lease expires and the item is claimed again; delivery stays idempotent by Event ID. Delivered rows are retained; removing them is not part of the initial capability and is not formal audit retention. The ordinary runtime role may update the outbox delivery state and read pending work as needed, but it has no DELETE right on the outbox. These mutable privileges do not grant update/delete rights on the formal Audit Event store. If the outbox write itself fails, the configured durable operational-event sink and critical alert are required; console logging alone is not a durable fallback.

### Retention Policy (Conceptual)

Represents an institutionally approved retention configuration applied through an authorized process. No duration is currently approved. The initial feature does not run deletion or archival. Any future archival preserves Admin retrieval and integrity protections; any deletion is a separately authorized, policy-governed process.

## Indexes and Query Shape

Planning targets the required filters and stable newest-first keyset pagination:

- Unique index on `EventId` for idempotent delivery and detail lookup.
- Composite index on `(OccurredAtUtc DESC, EventId DESC)` for deterministic search order/cursor pagination.
- Indexes on actor ID, event type, category, outcome, correlation ID, and `(EntityType, EntityId)` for supported equality filters.
- Outbox index on `(DeliveryState, NextAttemptAtUtc)` for pending/retry worker polling, plus unique Event ID.

The implementation should add only indexes justified by query plans and the measured representative data volume; large metadata/change-summary values are not indiscriminately indexed.

## Relationships and Transaction Boundaries

- Audit Event actor/entity identifiers are logical references, not cascading relational dependencies; history survives source-row removal.
- A future feature's mandatory business mutation and its Audit Event use the same `PortalDbContext`/PostgreSQL transaction. Both commit or both roll back.
- Security outbox insertion is persisted before asynchronous delivery is acknowledged. Formal audit-event insertion and outbox delivery-state change are idempotent across worker restart/replay.
- The runtime application role has append/read access to formal Audit Events, but no update/delete privileges. A separate DDL/migration principal owns schema objects and applies grants.
- The outbox and formal event store are logically distinct: retry-state updates never mutate a delivered formal event.

## Migration and Operations Impact

- Add version-controlled EF Core migrations for the formal event and security-outbox storage, supporting indexes, and runtime-role grants/configuration scripts.
- Migrations execute with the DDL owner through a separate migrations connection string, which `dotnet ef` uses. The API runtime uses a least-privilege credential; the current Development `postgres` connection is not acceptable evidence of the runtime permission boundary.
- The runtime role receives the rights it needs on every existing table and sequence, plus default privileges so tables created by later migrations are usable without further grants. Audit events are the exception: SELECT and INSERT only.
- Validate grants, uniqueness/idempotency, transactions, timestamp ordering, and PostgreSQL-specific schema using PostgreSQL 18. SQLite tests remain useful for service behavior but do not prove PostgreSQL grants or provider-specific SQL.
- Initial retention/archival jobs are absent. No delete/archive worker is scheduled until policy approval.
- Verify deployment configures a durable operational-event sink and alert for failure to enqueue a security event; otherwise FR-014 is not satisfied.
